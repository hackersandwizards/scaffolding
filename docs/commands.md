# Commands

Each command answers `--help` as its first argument with its usage line and its row of the table
below on stdout. `check-lock`, a skeleton file that runs without this file beside it, prints its usage
line and points here.

| `check-lock <command>`                            | `scaffolding check`, a build                                   | Runs the command once no other locked command runs in the checkout, so a build never rewrites the output a running gate reads (`"build": "check-lock astro build"`; first in the script, since the lock sits in `node_modules` where it starts, so `check-lock sh -c 'cd catalog && astro build'`). Inside a locked command, the gate's own build step included, it runs at once. Waiters take the lock in the order they came: a waiter renews its ticket every poll, the next waiter removes a ticket whose process is gone or that went unrenewed for 6 s. A waiter gives up after 15 minutes behind one holder, counted again whenever the lock passes on to another holder, not when the holder rewrites its own lock. A shorter `CHECK_LOCK_WAIT_MS` (an empty one is unset) gives up only on a live holder of another command or a lock path no waiter can reclaim (a directory, a file it cannot read): a holder running the same command is waited for in full, as is a free lock while a waiter ahead in the queue takes its turn, and for 6 s at least a dead holder's or unparsable lock, which the waiter ahead reclaims. `CHECK_LOCK_RUN_S` (unset, empty or 0: none) bounds the whole run, the wait included, in seconds: at the bound `check-lock` says so on stderr, stops as on a SIGTERM to it, kills the command 10 s later and exits 124, unless a signal came first. A signal to `check-lock`, or one that killed the command alone, goes to the command's whole process group, and the lock stays until that group has exited (a second signal kills it, as do 10 s after a signal the command took alone), also where a SIGKILL then ended `check-lock`; where a SIGKILL to the caller's group ended `check-lock` alone before any signal, until the command has exited; the command runs without a controlling terminal, so it cannot open `/dev/tty`. |
| `chrome-mcp [flag...]`                            | `.mcp.json`                                                    | The chrome-devtools MCP server this package pins (`chrome-devtools-mcp`), headless and isolated, on Chrome for Testing: `CHROME_BINARY`, else the build `puppeteer-core` pins, else the newest cached build, passing over one whose download archive still lies beside it (an install under way, waited for up to 2 minutes, or one that died), before `./chrome` installs one into a folder of its own and moves it into the cache whole, in place of a build whose install died; further flags go to the server, a later `--help` too (`chrome-mcp --headless --help` lists its flags). The skeleton's `.mcp.json` runs `.githooks/install` first and then `bun run --silent chrome-mcp` in `$CLAUDE_PROJECT_DIR`, so in a fresh clone it waits for the first install, its own or the SessionStart hook's, for up to 60 s (`CHECK_LOCK_RUN_S`, [Hooks and CI](hooks.md)). An install longer than Claude Code's MCP start timeout (`MCP_TIMEOUT`, 30 s by default) still fails the server: reconnect it with `/mcp`.                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                           |
| `raise-pins [--commit]`                           | a consumer, by hand or on a schedule                           | Raises every Git pin (`git+…#vX.Y.Z`) on a repository whose owner is `hackersandwizards`, on any host and whatever the package's name, to the newest `v` tag of its remote, a package after the pinned packages it depends on, with `bun install` after each and `check-structure --fix` after scaffolding's, under `check-lock`; a tag read ends after `SCAFFOLDING_FETCH_WAIT_S` seconds (20), and a pin whose tag is not read or that does not install keeps its version. Then, where a pin rose, `bun run check` once, and one line per package and one for the gate. With `--commit`, a green gate commits the raises that installed (`package.json`, `bun.lock` and the files `check-structure --fix` wrote, by name) unless `--fix` failed or rewrote a file holding an uncommitted change; it pushes nothing. It exits 1 where a pin kept its version, the gate is red, `--fix` failed or rewrote such a file, or the commit failed. It refuses to start without `bun.lock` or while `package.json` or `bun.lock` hold an uncommitted change. Without a commit the raise stays in those two files, and the next run refuses until they are committed or reverted.                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                       |

The gate and `check-staged` also run these files from `bin/` by path; they are steps, not commands,
so a new install links none of them into `node_modules/.bin`. A link to one is left from an install
before v0.9.0, which bun keeps: it still runs, since every file in `bin/` is stored executable, and
deleting it changes nothing for the gate.

## A new repository

`scaffold <dir> [--port <port>] [--name <package>]` (port 4600 and the folder's name by default;
a name npm would refuse stops it before it writes a file) writes the skeleton from `template/` (with an empty `docs/agent-work/` for the items) and the catalog
from `template-catalog/` (`catalog/astro.config.ts` on the preset with the Pages `site`,
`base: "/<name>"` without the name's scope, and the port, an example component and story,
`stylelint.config.js`, the scripts `dev`, `catalog`, `build` and `preview`, the Pages workflow,
and ESLint's Astro config with `eslint-plugin-astro`, so the `.astro` files are linted), and pins brand and admin to the newest tag on their remotes, so
an admin or brand release reaches new repositories without a scaffolding release. A repository whose
catalog or admin area lives in another repository leaves the catalog and brand out with
`--catalog-in <repo>`, or admin with `--admin-in <repo>`; its `scaffolding.skip` names that
repository. Registering the repository in
the hub's sync list, creating it on GitHub and switching Pages on stay steps for a person, which
`scaffold` prints after its own.
