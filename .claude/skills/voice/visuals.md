# Visuals

Show structure, order, dependency, status, options, change and time in the form this table names,
under one sentence saying what to see in it. Prose carries only what no form holds. A document written for one client takes its shape from
`brand-voice.md` first.

| The reader asks | Form | In a file | In a chat reply |
| --- | --- | --- | --- |
| Who does what, what contains what | Layers, top to bottom, one box per role or module | Mermaid `flowchart TD` | Table: role, does |
| What happens in which order | Chain, left to right, a loop as a back arrow | Mermaid `flowchart LR` | Numbered steps |
| What waits on what | Graph, the prerequisite on the left | Mermaid `flowchart LR` | Table: item, needs, state |
| Where each thing stands | Table: what, state, who moves next | Table | Table |
| Which option | Table: one row per option, the same criteria as columns | Table | Table |
| What changed | Before and after, side by side | Table, or the diagram with its changed edges listed under it | Table |
| When | Table sorted by time | Table | Table |

- A subject keeps its names, their order and, per medium, its form every time it is shown. A subject that
  outlasts the conversation is drawn once in a committed file and changed there; the reply shows
  its chat form and gives the path, again in the reply that reports a change to it.
- A diagram goes in a file, where T3's preview and GitHub render it; where the chat renders HTML
  (T3's `html_render`), a reply about structure, order or dependency also renders its diagram
  there as HTML, unasked. Elsewhere a chat reply uses the last column. No generated image.
- Mermaid source carries no colour, class or style line: the renderer themes it. Quote every node
  label that holds punctuation (`a["x: y"]`), or the diagram fails to parse.
- A diagram a tool can derive from code or records is generated by that tool, never drawn by hand.
